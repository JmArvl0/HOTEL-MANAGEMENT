# 2026-09-09 — Session 02: Required payment-proof upload for reservation deposits

**Scope:** `/booking/payment/[token]` — the guest must now submit BOTH a transaction reference AND
a payment-proof screenshot (JPEG/PNG/WebP, ≤5 MB) before a manual GCash/bank-transfer deposit can
be submitted for Accounting verification. The manual verification model itself is unchanged
(no gateway, no automation, Accounting-only authority preserved at every layer).

## What changed

- **Migration `20260921010000_payment_proof.sql`** (applied via `supabase db push`, live-verified):
  5 nullable `proof_*` columns on `payments`; **private** `payment-proofs` storage bucket
  (5 MB, jpeg/png/webp, zero policies); `submit_reservation_deposit` recreated from the LIVE remote
  body (which had drifted from the migration file — carries `operational_policy_snapshot`,
  `room_is_sellable`, transport folio lines) + new proof params and a `PROOF_REQUIRED` guard.
  Grants revoked from public/anon/authenticated, granted to service_role.
- **`lib/payment-proof.ts`** (new) — magic-byte sniffing (JPEG/PNG/WebP), 5 MB cap, staged-path
  pattern `pending/<token>/<uuid>.<ext>`, filename sanitizer.
- **`app/api/booking/holds/[token]/proof/route.ts`** (new) — POST stages the upload (hold-owner +
  active-hold guarded, sniffs bytes, uploads via service role); DELETE removes a staged path
  (regex-validated against this hold's namespace).
- **`app/api/booking/holds/[token]/confirm/route.ts`** — `depositSubmissionSchema` now requires
  `proofPath`; the route re-downloads the object, re-sniffs and re-measures before the RPC, and
  removes the staged upload on RPC failure (idempotent replays keep the original). `PROOF_REQUIRED`
  added to the error map.
- **`app/api/booking/payments/[id]/proof/route.ts`** (new) — 60-second signed URL; access is the
  paying guest (payment→reservation.user_id) or Accounting ONLY; 404 for everyone else.
- **`components/booking/confirm-booking-form.tsx`** — upload area with client pre-validation,
  staged-upload → confirm two-step submit, Replace/Remove, submit disabled until reference AND
  proof are present, uploading/submitting states. On permanent failure the staged upload is
  released.
- **`components/manager/manager-dashboard-client.tsx`** — DepositVerifyDialog gains a
  Proof-of-payment metadata row + `ProofPreview` (fetches the signed URL on open, branded modal,
  loading/error fallbacks). Same Verify/Reject endpoints — no second verification mechanism.
- **`lib/staff-data.ts`** payments select + `lib/customer.ts` reservation detail select gain the
  proof metadata columns; confirmation page shows a read-only proof thumbnail (owner route).
- **`SYSTEM.md`** — §7.1 (bucket note), §7.2 (full proof workflow), §10 (RPC row), §11 (routes),
  §13 (untrusted-client bullet).
- CSS: scoped `.proof-*` styles in `guest-booking.css`; `.deposit-proof*` in
  `manager-dashboard-theme.css`.

## Notes / risks

- Resubmission after a rejected deposit does not exist by design: the existing reject path cancels
  the reservation (guest books again), so rejected-attempt history is the `failed` payment row +
  `decision_reason` — preserved, not overwritten.
- Stay-payment proof (`customer_submit_stay_payment`) still takes a reference only — out of scope.
- ⚠️ An accidental `git stash` fired mid-session; `git stash pop` restored everything (verified
  file-by-file). Don't stash this tree (known memory).
