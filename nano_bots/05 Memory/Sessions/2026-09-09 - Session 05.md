# 2026-09-09 - Session 05 — Manager/Accounting workflow revision (D-007)

## Objective

User directive: analyze and revise the MANAGER and ACCOUNTING workflows (business logic + data
flow + RBAC + UI/UX) to remove unnecessary Accounting↔Manager loops. CORE DECISION: Accounting
owns normal financial operations; Manager owns financial exceptions and operational oversight.
Audit first — no code changes before the real project was inspected end-to-end.

## Audit result (the load-bearing finding)

The backend **already enforced the target model at every layer** — verified across
`lib/permissions.ts`, all manager/accounting route guards, and the newest RPC bodies
(20260912020000, which superseded the 20260829 approval bodies):

- Policy refunds need no Manager: `cancel_reservation` computes the entitlement from the frozen
  `operational_policy_snapshot` and inserts `refund_requests` with `exception_approval_id NULL`;
  Accounting settles directly (`process_refund`, idempotent, `REFUND_EXCEEDS_RECEIVED`).
- Refund exceptions: `request_manager_approval` (closed reservation required, policy baseline
  recorded) → `review_manager_approval` (≤ settled deposit − already refunded; approved amount
  fixed into `eligible_amount` with `normal_policy_amount`) → Accounting `process_refund` →
  `refund_completes_manager_approval` trigger stamps execution. No re-approval loop.
- Guest compensation: Accounting executes once as a credit
  (`accounting_execute_manager_financial_approval`; unique index blocks double execution).
- Manager has zero financial execution flags and no financial dashboard sections.

**No migration, no new RPC, no permission-flag change was needed.** The gap was that the refund
queue could not *show* the distinction it enforced.
